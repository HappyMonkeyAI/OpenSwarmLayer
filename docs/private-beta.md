# Private model-sharing beta

TensorSwarm is experimental. The current private sharing flow uses a signed
release bundle, a separate manifest, and an explicitly supplied peer identity
and reachable address. A `tswarm://` identifier binds the signed metadata; it
does not resolve a peer or start a download. No public tracker or model search
is available.

## Desktop transfer

1. On the sender, import a small GGUF or Safetensors file you may redistribute.
   Wait for verification and an online engine. Select the model and export its
   `.tswarm` manifest and signed `.tsrelease` bundle using the desktop controls.
2. Send those metadata files and the exact share identifier to the recipient.
   Share the current peer ID from **Peers & sources** separately. A signature
   made by an embedded key does not establish a publisher's real identity.
3. On the recipient, open **Model library**, enter the received identifier, and
   choose the signed bundle and matching manifest. This creates a checked
   metadata receipt without adding model bytes to the library.
4. Choose **Download from peer**, supply the sender's identity and reachable
   multiaddress, and select a new output file. Only verified chunks count toward
   progress. On completion, confirm the engine is online and the model has 100%
   verified availability before sharing it onward.
5. Stop the original sender. Use a third peer with a fresh cache to download from
   the recipient. Compare the complete output with the source and verify it
   against the manifest. This demonstrates re-sharing rather than cache reuse.

The library currently requires one artifact format and rejects model-path
conflicts. Output files must be new and on a filesystem supporting hard links.
Only one private download runs at a time. Cancellation applies during fetching;
verified partial chunks remain for retry, including after restart. Download
caches currently have no automatic quota or cleanup. Restart changes the peer
identity and listening ports, so always read current connection details.

## Temporary Cloudflare TCP bridge

This external test harness was exercised with Windows cloudflared 2026.9.3 and
Mint cloudflared 2025.8.1. TensorSwarm itself does not install or manage it.

On the sender, find its current TCP listening port and run:

```text
cloudflared tunnel --no-autoupdate --url tcp://127.0.0.1:<peer-port>
```

Keep it running and record the returned `https://<name>.trycloudflare.com` URL.
On the recipient, run:

```text
cloudflared access tcp --hostname <name>.trycloudflare.com --url 127.0.0.1:44499
```

Supply `/ip4/127.0.0.1/tcp/44499` in the recipient desktop download form, together
with the sender's actual peer ID. The URL alone is not a TensorSwarm peer
address. Both cloudflared processes must remain running during the transfer.
Expose only the peer listener; keep the authenticated control API private.
Stop the test tunnels when finished. A restarted seed needs a tunnel targeting
its new port and the recipient needs its new peer ID.

For re-sharing, reverse the roles: expose the recipient desktop's peer listener,
create a client bridge on the third peer, and fetch with the recipient's current
identity into a fresh cache. A CLI recipient can use:

```text
ts-cli receive-release release.tsrelease model.tswarm fresh-inbox tswarm://v1/<release-id>
ts-cli fetch-received fresh-inbox/<release-id> <peer-id> /ip4/127.0.0.1/tcp/44499 fresh-store downloaded.safetensors
ts-cli verify downloaded.safetensors model.tswarm
```

`verify` checks the supplied chunk layout, canonical tensor identities, and file
recipe against the actual model. A local filename may differ from the manifest's
distribution filename. It expects a single-file recipe generated by the format
builder; arbitrary alternative recipe encodings are not accepted.

## Evidence and release gates

On 2026-10-03 a fresh Windows desktop profile downloaded an eight-chunk synthetic
Safetensors model through Cloudflare, activated it, retained 100% availability
after restart, and re-shared it through another Quick Tunnel after the original
Mint seed stopped. A fresh Mint CLI peer produced byte-identical output.
Both machines were on one LAN: this is external relay transport evidence, not
separate-network or native desktop-to-desktop acceptance. See `PROGRESS.md`.

On 2026-10-03/04 the current source also passed an isolated Windows NSIS
installation, empty first launch, native download and activation, restart
persistence, Cloudflare re-sharing to a fresh Mint CLI cache, full-byte
comparison, and silent uninstall. The acceptance package used a distinct
product name and application identifier to preserve the existing installation.
The production installer built successfully but its default-profile installation
and upgrade path were not exercised. Both installers are unsigned. Native
metadata pickers were tested in the earlier debug run; the packaged test staged
checked metadata with the CLI before native download.

Before describing the intended internet desktop beta as accepted:

- Repeat on separate internet connections, retaining command access and recording
  the network arrangement. Use fresh recipient caches and stop the original seed
  before the re-sharing leg. The owner deferred this test to a later friend pilot.
- Complete native Linux desktop/package/tray acceptance and native desktop-to-
  desktop transfer. WSLg and CLI peers do not close these gates.
- Review the exact release files and Git diff, run the verification ladder, build
  current installers, and record checksums and clean-install results. Isolated
  current-source Windows package acceptance passes; production-profile upgrade
  and native Linux package acceptance remain open.
- Keep signing credentials, models, machine-local configuration, scratch test
  files and build output out of Git. The project's intended license is MIT.

Publishing source as an experimental beta does not enable a public directory,
automatic rendezvous or NAT traversal. Those remain separate product work.
